# Decision Log — Boston Startup Tracker ServiceNow Replatform

The single source of truth for **why** every non-trivial choice in this delivery was made the way it was.

The delivery replatforms the Boston Startup Tracker — a tracker of venture-backed companies headquartered in the Boston area — from a Flask, React, PostgreSQL, Redis, Elasticsearch, Celery and Docker scaffold onto the ServiceNow Now Platform, as one scoped application: `x_bst_startuptrk`, vendor prefix `x_bst`, version `1.0.0`.

## Purpose and Rule 1 compliance

This file is the deliverable required by **Rule 1 (Explainability)**. That rule requires every non-trivial implementation decision to be documented with rationale, defines a decision as non-trivial when a competent engineer could reasonably have chosen differently, and requires the record to take the form of a Markdown table stating what was decided, what alternatives existed, why the choice was made and what risks it carries. Those four things are the four substantive columns of every table below.

Rule 1 imposes three further obligations that shape this file:

1. **The non-trivial test is the inclusion criterion.** A choice with exactly one sane option earns no row. Defining tables through the platform's table dictionary, for instance, is not a decision — there is no other mechanism. Storing `portfolio_count` rather than computing it on every read is a decision, because both are workable and a competent engineer could have picked either.
2. **Every deviation from a literal or obvious reading of the requirements has its own explicit row**, because Rule 1 treats an unexplained deviation as a defect. Twenty-five rows are so marked, and [Index of deviation rows](#index-of-deviation-rows) lists every one.
3. **No rationale lives in code.** Script Include headers, business rule comments and platform record `description` fields in this delivery state only what an artifact does and which requirement it implements. They are pointers, never arguments. Every *why* is here.

Fourteen documents in the deliverable package state that they carry no rationale and defer every *why* to this file. This file is therefore written to be **self-contained**: it never sends a reader elsewhere to find a reason. References to sibling documents below point at *specifications* — what a thing is — never at explanations.

## How rationale is partitioned

| Question | Where it is answered |
| --- | --- |
| **What** an artifact is, and which requirement it satisfies | The deliverable package documents, and the `description` field of each platform record |
| **How** to build or deploy it | The six manual-build guides and the deployment runbook |
| **Why** it is that way, what else was considered, what risk it carries | **This file, and only this file** |
| **Which** source construct or requirement each artifact traces to | `docs/decisions/TRACEABILITY_MATRIX.md` |

Rule 1 bundles a second obligation into the same clause as the decision log: for a migration or refactor, a **bidirectional traceability matrix** mapping source constructs to target implementations at full coverage with no gaps. That obligation is discharged by the sibling file **`docs/decisions/TRACEABILITY_MATRIX.md`**, not here, and this log deliberately duplicates none of its content. Both halves must exist for Rule 1 to be satisfied.

## Behaviour preservation is not the invariant

Ordinary migration logic — preserve observable behaviour, change only the implementation — does not apply here, and saying so up front prevents a whole class of misreading.

**The legacy application cannot start.** Twelve broken references were verified directly in the tree. The continuous-integration workflow installs from a requirements file that does not exist [`.github/workflows/ci.yml:L24`] and then runs a frontend install in a directory that has no manifest [`.github/workflows/ci.yml:L36-L37`]. The root manifest declares an entry point that is absent [`package.json:L5`] and is not valid JSON in any case, because a comment block begins after the closing brace [`package.json:L65`]. The test configuration collects files matching a leading `test_` [`pytest.ini:L9`] while all 21 test modules on disk carry a trailing `_test.py`, so 0 of 27 test files are collectable. A `src/utils/` package is imported by three modules [`src/data_collection/api_integrators/crunchbase_integrator.py:L8`] and does not exist. The single-page application imports a theme module [`src/frontend/App.tsx:L12`] that was never authored — `src/frontend/styles/` contains only `global.css`. Three Compose services declare a Dockerfile [`docker-compose.yml:L6-L8`] that exists nowhere in the tree.

There is consequently **no runtime behaviour to preserve**. What is preserved instead is the **domain-model semantics** — the entities, their relationships and their meaning — and the **route and entity inventory**. What is deliberately *not* preserved is the API contract, the field list, the enumerations, the role model and the cleaning rules, every one of which the requirements re-specify. The safety mechanism substituted for incremental behaviour comparison is deployment-level: validate, preview, require an empty error-type problem set, commit, gate, and roll back on failure.

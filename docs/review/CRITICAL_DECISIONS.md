# Critical decisions — Boston Startup Tracker on ServiceNow (`x_bst_startuptrk`)

## Purpose and scope

This is the review artifact required by the project rule **Critical Decision Review Document**. It lists the five highest-risk and most consequential decisions made while replatforming the Boston Startup Tracker from its non-functional Flask, React, PostgreSQL and Celery scaffold onto the ServiceNow Now Platform as the single scoped application `x_bst_startuptrk`. Each entry states what was implemented and what alternatives existed, why the choice was made with a citation a reviewer can follow, the risk it carries, and the one named reviewer who should validate it together with exactly what to check.

**This document is not the decision log.** It is a triage instrument for five reviewers, deliberately short. The authoritative record of every non-trivial decision in this delivery, with its full set of alternatives, its rationale and its risks, is [`../decisions/DECISION_LOG.md`](../decisions/DECISION_LOG.md), required by the project rule **Explainability**. The bidirectional source-to-target traceability matrix required by the same rule is [`../decisions/TRACEABILITY_MATRIX.md`](../decisions/TRACEABILITY_MATRIX.md).

Everything outside those five entries — the **three hundred and seventeen** further decisions this delivery made, the requirement coverage, the retired components, and the reverse lookups from artifact to justification — belongs to those two documents and is not duplicated here. A reviewer who needs the whole picture reads the log. A reviewer who needs to know what to scrutinise first reads this.

## 1. Field-level access control as the premium entitlement boundary — risk High — reviewer persona Security

### Decision

**What was implemented.** The authorisation decision was moved out of application code entirely and into the platform's access-control engine. The application declares three roles, whose names are fully qualified and dotted with no underscore form: `x_bst_startuptrk.admin`, `x_bst_startuptrk.premium_user` and `x_bst_startuptrk.user`. Both non-administrative roles are read-only; `x_bst_startuptrk.admin` is the only role that can mutate a record on any surface.

Enforcement is **49 `sys_security_acl` records** — 47 of type `record` and 2 of type `REST_Endpoint` — with **74 `sys_security_acl_role` join records**, arranged in five layers:

| Layer | Scope | ACLs | Role joins | Grants |
| --- | --- | --- | --- | --- |
| 1 | Table-level read, seven entity tables | 7 | 21 | All three roles |
| 2 | Table-level write, create and delete, seven entity tables | 21 | 21 | `x_bst_startuptrk.admin` only |
| 3 | **Field-level read, the seven premium fields** | 7 | 14 | `x_bst_startuptrk.admin` and `x_bst_startuptrk.premium_user` only |
| 4 | Supporting tables, all four operations on each of three | 12 | 14 | The join table readable by all three roles so participation renders; the staging and rate-limit-counter tables administrator-only |
| 5 | REST endpoint execution | 2 | 4 | `Boston Startup Tracker API read` to all three roles; `Boston Startup Tracker API write` to `x_bst_startuptrk.admin` only |

Layer 3 is the entitlement boundary. The seven gated fields are exactly `x_bst_startuptrk_startup.total_funding_usd`, `x_bst_startuptrk_startup.institutional_funding_last_5yrs`, `x_bst_startuptrk_founder.contact_email`, `x_bst_startuptrk_executive.contact_email`, `x_bst_startuptrk_investor.aum_usd`, `x_bst_startuptrk_fundinground.amount_usd` and `x_bst_startuptrk_fundinground.valuation_usd`. There is no eighth. `contact_email` is gated on two tables and is a distinct access control on each.

Three enforcement rules bind every calling surface equally, so the API and the portal cannot disagree about what a role may see. Every caller-facing read uses the **secured** record-access path, never the unsecured one. The response serialiser applies a **per-element read check** and, where it fails, **omits the key from the response object entirely** — it is never nulled, emptied, zeroed or dashed. Every one of the 31 REST operations requires both authentication and access-control authorisation and names the layer-5 control it consults; none of the eight Script Includes is client-callable, mobile-callable or sandbox-callable, and none reads a premium field through an unsecured path on a caller's behalf.

Beneath the access controls sits a scope posture that decides which routes reach the rows at all, and it is **uniform across all ten tables: every one of them is sealed**. All ten ship `access` `package_private` with `read_access` and `ws_access` false, and with every cross-scope write, schema and configuration flag false — `create_access`, `update_access`, `delete_access`, `alter_access` and `configuration_access`. Nothing outside the scope reads or writes application data by any route. `GET /api/now/table/x_bst_startuptrk_startup` answers `HTTP 400 Invalid table` to every caller including an instance administrator. That is deliberate and it is load-bearing, because a field-level read control omits a value from a *response* and three native routes obtain the same value without one ever being serialised: a query predicate such as `total_funding_usd>50000000`, which the database evaluates before serialisation so bisection recovers the figure; the native Aggregate API, which returns a computed sum with no element on which a field control could be evaluated; and unsecured record access from another application scope, which consults no access control at all. None of the three is fixable inside the access controls, which is why the posture and not a further control is where they are closed. Sealing also removes a list route that sat outside the inclusion plan and outside the fixed-window rate limiter. The Scripted REST API is therefore the whole of the caller-facing surface: 31 operations, each requiring authentication and endpoint authorisation, each reading through the secured path, each omitting denied keys, each applying the inclusion plan and each passing through the limiter. The cost is that a sealed table cannot be verified by reading a row, so the seven required post-commit gates read each table's `sys_db_object` definition record and assert its three posture values, and the class-3 diagnostic `GATE-SEC-04` opens each entity table through the secured path from inside the scope. Both are in [`validation-gates.md`](../../servicenow-startup-tracker-poc/docs/validation-gates.md), and the residual risk is recorded in [`gaps-and-flags.md`](../../servicenow-startup-tracker-poc/docs/gaps-and-flags.md). One property of the surviving route is worth stating so no reviewer over-reads it: the rate limiter on it is a fair-use control and **not** a security boundary — a caller inside its budget is still subject to every access control on every field it reads. The decisions are `D-027` and `D-254`, **amended by `D-310` and `D-311`**: `D-310` seals all ten tables uniformly, and `D-311` expresses the seven required table gates as the `sys_db_object` metadata read described above and adds the fourth class-3 diagnostic `GATE-SEC-04`. The departure from AAP section 0.11.2's literal row read is accepted by name, as a recorded human acceptance rather than an argued equivalence, at `D-455`.

**What alternatives existed.**

- **Hide the fields in the interface only**, through form layout or display rules. Rejected: the requirement is a genuine access denial, not a hidden form field, and a hidden field is still readable by any other route to the record.
- **Keep authorisation in application code**, carrying the legacy decorator pattern forward. Rejected: it reproduces the legacy failure mode described below, and the requirements forbid the REST layer from bypassing access control.
- **Table-level ACLs only.** Rejected: the platform then falls back to the table-level grant and every premium field becomes readable by every role.
- **Field-level ACLs only.** Rejected in the opposite direction: without a table-level read grant nothing is readable at all, and the field-level rules never evaluate.
- **Return `null` or an empty string for a denied field.** Rejected: the requirement is omission, and an empty value is indistinguishable from a genuinely empty column.
- **A single premium-role check inside one serialiser, without ACLs.** Rejected: it is a single point of enforcement that any newly added read path can simply forget, and the platform would report no denial because it was never asked.
- **Leave the seven entity tables `access` `public` and rely on the field-level controls**, as an earlier build did. Rejected: a cross-scope `GlideRecord` read does not evaluate them, so the boundary would exist only for callers who chose to respect it.
- **Leave them `public` and add record-level rules to compensate.** Rejected: it guards the extra route instead of removing it, and it would additionally break the `total_count` invariant, which is only correct because record-level visibility is identical for all three roles.
- **Close them and drop the seven post-commit table gates as unrunnable.** Rejected: the gates are frozen at eleven and a dropped gate is lost evidence. They were re-expressed against table **metadata** instead, which asserts the closed posture rather than a successful read.

### Rationale

The legacy application had no authorisation at all, and this is verifiable rather than asserted. `src/backend/utils/auth.py:L6-L16` defines the `auth_required` decorator: it applies `@jwt_required()` at `:L8` and wraps the decorated function in a `try`/`except` returning `{"error": "Authentication required"}` with status 401 at `:L15`. Across the whole 42-line file there is no role parameter, no role argument and no role comparison of any kind. It performs authentication only.

The file records the gap in its own text. `src/backend/utils/auth.py:L36` reads `# TODO: Implement role-based access control`, and `:L42` reads `# TODO: Add additional claims to the token (e.g., user role)`. Read together these establish something stronger than "unimplemented": the access token carried no role claim, so a role check was **not possible** with the token as issued. Meanwhile `src/shared/types.ts:L72-L76` declares `export enum UserRole { ADMIN = 'ADMIN', USER = 'USER', PREMIUM_USER = 'PREMIUM_USER' }` — three entitlement tiers named in the type system and enforced nowhere. The requirement they were meant to serve is `documentation/Software Requirements Specifications (SRS).md:L77`, "Role-based access control (free users, premium subscribers, administrators)", whose "free users" tier becomes the base `x_bst_startuptrk.user` role.

Two platform conventions determine the shape of the replacement.

**The evaluation chain requires a pass at every level, and it is matched most-specific-first** — a table-and-field rule outranks a table-wide rule, which outranks a global rule. This is why both layer 1 and layer 3 are mandatory, and why omitting either fails *silently* and in opposite directions: layer 1 without layer 3 leaves every premium field readable; layer 3 without layer 1 leaves no record readable and the field rules never fire.

**The secured read path returns an empty string for a denied field rather than raising.** Serialising every column of a secured record therefore produces exactly the nulled shape the requirements forbid. Omission is not a by-product of using the secured path; it demands a deliberate per-element check and deletion of the key, which is why the gate lives exactly once and every surface is required to route through it.

The delivered scheme, its five layers, its 21-cell role-by-field matrix and its verification procedure are enumerated in [`access-control.md`](../../servicenow-startup-tracker-poc/docs/access-control.md). Two figures deserve stating precisely, under the authority rule above. The plan states the access-control and role-join counts as **approximations** — roughly 43 and 64 — and the delivered 49 and 74 satisfy them as approximations; that is a match, not a licence to have exceeded anything. The **fifth layer is a genuine addition** to the plan's four, and it is carried as a **logged deviation** rather than a silent one: `D-027` records it and the log's deviation index carries it. It exists because a Scripted REST API without an endpoint-execution control falls back to a platform default that any authenticated internal user satisfies, so omitting the layer would leave the API authorised by something other than this application's own controls.

### Risk level

**High.** Three factors compound.

This is the authorisation boundary of the application, and the data behind it is the commercially valuable part of the dataset: funding totals, round amounts, valuations, investor assets under management, and the contact email addresses of named individuals. Getting it wrong is a data-exposure incident, not a defect report.

Both failure modes are **silent**. Nothing readable, or everything readable — neither raises an error, neither appears in a log, and neither is visible to a caller who is not specifically looking.

Worst, **the administrator override makes a naive verification actively harmful.** All 49 access controls carry `admin_overrides` true, so the platform administrator role overrides every one of them, and every operator of a personal developer instance holds that role. A walkthrough performed while signed in as the instance administrator displays all seven premium fields and **appears to prove enforcement that was never tested at all**. That is worse than no verification, because it manufactures documented false confidence. The scoped role `x_bst_startuptrk.admin` and the platform administrator role are different roles, and conflating them is the specific mistake that produces this outcome.

## 2. Rollback branched by starting state, behind a 313-record Update Set — risk High — reviewer persona DevOps

### Decision

**What was implemented.** The legacy application cannot start, so there is no working prior version to fall back to and no incremental code path to retreat along. Deployment-level safety therefore substitutes for code-level incrementalism: a validate-then-preview-then-commit lifecycle with a documented rollback.

The sequence has four stages.

**Pre-delivery validation.** The two-level XML validator runs against the file on disk before anything touches the instance, covering gates **G-1** (the outer `<unload>` document) and **G-2** (every `<payload>` un-escaped and parsed as an independent `<record_update>` document). Exit `0` proceeds; `1` is a validation failure; `2` is a usage or unreadable-path error and takes precedence over `1`. **A non-zero exit blocks the deployment.** The validator covers G-1 and G-2 only — a file that exits `0` is not thereby certified against G-3 through G-9.

**Environment validation, then five instance prerequisites, then three pre-flight checks** — in that order, all before the upload. Environment validation asserts that `SERVICENOW_INSTANCE_URL` is present and well-formed and that both credential variables are non-empty, before any request is issued and without printing the password. The five prerequisites are the `admin` role; the release floor; the instance's XML entity-resolution properties, which this application can neither set nor test into compliance and which are therefore asserted before the import rather than gated after the commit (`D-256`); ATF execution enabled with a test-designer role held, without which the coverage gate cannot be evaluated at all; and the recorded readiness path for the two credential aliases, the one entry of the five with two valid outcomes rather than a pass and a fail.

**The release floor is established objectively rather than recorded.** The family token is extracted from the instance's own `glide.war` value and compared against an ordered release list, and a family the list places below `yokohama` — or a value that does not parse into a family token at all — **aborts the deployment**, carrying the requirement's own instruction to request a new instance rather than downgrade feature usage. The list is explicit because the release naming restarted the alphabet, so a lexical comparison is wrong: `australia` is later than `zurich` despite sorting earlier. **The same read is then compared a second time, against the security patch baseline**, because the feature floor and the patch baseline are different questions: an instance can sit far above `yokohama` and still be below the patch level at which the known unauthenticated platform sandbox escape was fixed. That comparison has its own abort branch, and the runbook deliberately **declines** the vendor's interim mitigations — all of them outside the application's scope, and the principal one a one-way instance change that cannot be undone.

**Three pre-flight checks** then run, exactly the three the deployment environment defines. Check 1, the instance is reachable and the credentials are valid. Check 2, the scope's existence is **logged and is never a gate**: an existing scope is not an error, because the commit updates existing records and the preview surfaces any real conflict. Check 2 is not decoration either — it records the **installation mode**, `clean install` or `upgrade install`, and that record is what later permits or forbids the rollback, because once a commit has run a scope exists either way and nothing observable distinguishes one this deployment created from one it updated. Check 3, the instance is not mid-upgrade.

**A six-step import sequence**, three of whose steps run over an authenticated form session rather than the table API, because the documented table-API forms of the upload and the preview do not work on this platform. One session is established once, with a permission-restricted cookie jar and a non-empty `sysparm_ck` asserted before it is used, and all three steps use that same jar. Upload the raw XML under a **unique run name** — a clone index and a timestamp nonce — and capture the resulting record **by that name**, requiring exactly one new match rather than taking the first element of a list; poll until `loaded` at 5-second intervals with a **300 s** timeout; trigger the preview and poll until `previewed` at 5-second intervals with a **600 s** timeout; require the **error-type** preview-problem set to be **empty** while logging warning-type problems without aborting; then, as a precondition of the commit rather than a member of the gate set, require `PRE-COMMIT-01` and `PRE-COMMIT-02` — both defined in [`../../servicenow-startup-tracker-poc/docs/deployment-runbook.md`](../../servicenow-startup-tracker-poc/docs/deployment-runbook.md), and deliberately absent from the eleven-gate set in `validation-gates.md` — to confirm all **313** records arrived and previewed; commit in three phases — validate, **assert the validation answer**, then commit and poll until `committed` at 10-second intervals with a **1200 s** timeout — where the assertion is four checks on the processor's response and any one of them failing aborts **without committing**; then run the post-commit gates.

**Eleven required post-commit gates, and only those eleven.** They are `GATE-TBL-01` through `GATE-TBL-07` for the seven entity tables, `GATE-ROLE-01` through `GATE-ROLE-03` for the three roles, and `GATE-SCOPE-01` for the scope record — exactly the set the deployment environment mandates, and exactly the set the Agent Action Plan fixes at 7 plus 3 plus 1. Each table gate is a **direct authenticated read of one entity table**. All eleven are required: there is no partial pass among them, none is advisory, and none may be skipped, deferred or waived, and the aggregate pass condition is `11 of 11`.

**Five further checks sit beside that set in two classes, and they are counted separately from it and from each other.** **`GATE-COL-01`** — the 53-column count — is **acceptance-required and non-rollback**: success criterion 1 depends on it, so a failure blocks acceptance, but the remedy is to correct the Update Set and re-import rather than to delete a scope whose seven tables and three roles all committed. **`GATE-SEC-01` through `GATE-SEC-03`** — the scope-containment, cross-scope-write and REST-control posture checks — are **acceptance-required and non-rollback on the same terms**: each names an exposure the required eleven cannot see, so a failure blocks acceptance, and the remedy is a correction and a re-import or a written acceptance of the named exposure recorded by the platform owner. **`GATE-SEC-04`** — the secured-read-path check — is the single **non-normative diagnostic**, because it is the one check that is not an HTTP request but a background script a human runs in the platform UI, so no deployment pipeline can assert on it; it is recorded on every deployment and decides nothing. `GATE-COL-01` asserts that the seven entity tables carry exactly 53 columns between them, and all five checks are recorded as evidence whatever their outcome. **No `GATE-SEC` check may be cited as an entry condition by any document in this package** — a rule the six manual-build guides and the build index were written to honour, and one that is compatible with the class blocking acceptance, because an entry condition and an acceptance condition are different things. One condition sits outside every class: the Global-scope XML entity-resolution configuration an earlier revision gated on is instance configuration this delivery neither creates nor can set, so it is a read-only external prerequisite owned by the platform owner, with no remediation and no rollback semantics attached to it. So **fifteen checks block acceptance and eleven of them trigger the rollback**; the classes and the asymmetry are recorded at `D-108` and `D-417`, and the count is reconciled across the package at `D-522`.

**The rollback runs on exactly two conditions** and no others: a commit failure at step 5, or the failure of any of the **eleven required** gates at step 6. Neither a `GATE-COL-01` failure nor a diagnostic failure is one of them: each is recorded and investigated, and neither ever rolls back. A `GATE-COL-01` failure does, however, block acceptance. Nothing else triggers the rollback either: not a pre-flight failure, not an upload or load failure, not a preview error, not an error-type preview problem, not a pre-commit completeness shortfall, and not any of the timeouts — each has its own non-destructive row in the failure matrix.

**Which rollback runs is decided by the starting state, not by the trigger.** Pre-flight 2 sets `START_STATE` before anything touches the instance, and the rollback reads that value rather than re-deriving it:

- **`START_STATE=clean`** — the scope did not exist before this run, so everything inside it was created by this commit. **Branch A: scope deletion.** Retrieve the `sys_scope` record for `x_bst_startuptrk`, delete it so its tables, roles and flows cascade, and confirm the cascade by reading table **metadata** for an empty result. It destroys all ten tables and all data in them, the three roles, and every artifact inside the scope — including flows, portal records and ATF suites built by hand after the commit, which means guides 01 through 06 must be re-run in full. Because this run created all of it, the blast radius is bounded by this run.
- **`START_STATE=existing`, or unknown** — the scope was already installed and this run was an upgrade over it. **Branch B: back the committed update set out, and never delete the scope.** Stop making changes, read and record what the commit applied, use the platform's Back Out action on this run's retrieved update set interactively, re-run the eleven required gates against the backed-out instance, and escalate to a named owner where the backout cannot restore the prior state. Branch B destroys nothing: it deletes no scope, no table, no role and no update set.

**Scope deletion applied to an installation this run did not create is not a rollback — it is total data loss**, taking ten tables of somebody else's data plus every manually built artifact in their scope. That is why the branch is fixed at pre-flight rather than chosen under pressure at step 5, and why `START_STATE=existing` additionally requires, before the upload is even attempted, both a backup or a written expendability statement from the application owner **and** the identity of the currently committed set to back out. If either is unavailable the run **aborts** at pre-flight, having touched nothing.

**A trigger condition makes the rollback applicable, and being applicable is not the same as being permitted: five preconditions make it permitted, and if any one of them does not hold the rollback does not run.** They are: the installation mode recorded at pre-flight 2 is `clean install`; **exactly one** `sys_scope` record for `x_bst_startuptrk` exists now; that record's `sys_id` equals the one `GATE-SCOPE-01` returned during this run; the trigger condition is one of the two above and has already been reported in writing; and the operator supplies a confirmation token naming this run and this scope identifier, typed at the moment of the deletion. Zero scope records means there is nothing to roll back and the procedure stops; **more than one, or an identifier that differs, stops and escalates** rather than choosing between them. The deletion is issued against `{scope_sys_id}` and never against a query, and the runbook states the rule that the delivered procedure had broken: never take `result[0].sys_id` from an unchecked array.

On a permitted rollback the scope record is deleted so its tables, roles and flows cascade, and the removal is then confirmed **on five surfaces** rather than one, because a cascade can remove a table definition while leaving a role behind, or remove the three roles while leaving every grant that pointed at them: no `x_bst_startuptrk_` table definitions remain; no dictionary record for any of the ten tables survives; no `x_bst_startuptrk.` roles remain; no scope record remains; and **no `sys_user_has_role` row still names one of the three application roles**. **A rollback whose five confirmations do not all pass is an incomplete rollback**, and the instance is not clean.

**The fifth surface carries a step of its own, and it blocks re-deployment.** The three role `sys_id`s are deterministic values in the delivered Update Set — `2628c956f9c80c23bcdf652eb2e41cec`, `ab589794d8f6b8de89b0716efcdc7f0f` and `47685e1edeb6c649bd3248e82bd3a582` — so a re-deployment recreates the three roles carrying the identical identifiers. Deleting the scope removes the `sys_user_role` records but **not** the `sys_user_has_role` rows that pointed at them, because those live outside the application scope. Every surviving grant therefore **re-attaches silently** when the roles come back, handing its holder the privilege it names — an administrator grant most of all — with no second grant and no record of a decision. Step A6 of the runbook snapshots those rows, deletes each **by `sys_id`** rather than by query, and proves the remaining count is **zero**; re-deployment is blocked until it does, and the next run's pre-flight re-reads the same query. Re-granting afterwards is a deliberate, separately authorised act that reads from the snapshot.

The failure matrix places every other condition elsewhere: abort on a pre-flight authentication or authorisation failure; fix and re-export on a load error, a preview error or any error-type preview problem; abort and investigate on any of the timeouts without rolling back. **The retry policy is stated per operation class rather than per status**, because a single "retry any server error once" rule is safe for a read and unsafe for a write: reissuing an upload creates a second update set and reissuing a commit applies records twice. Idempotent reads retry once after 30 seconds. The upload never blind-retries — it re-queries by run name first, treats exactly one match as success, retries only on none, and stops on more than one. The preview re-reads the state and reissues only from `loaded`. **The commit is never retried under any circumstance.** A delete is never retried; its outcome is re-read by `sys_id` and reported. An operation-specific rule always takes precedence over the general one. A gate failure is reported **by its specific gate identifier** before the rollback is initiated.

**What alternatives existed.**

- **Split the delivery into several smaller update sets** to stay inside the practitioner comfort guideline of roughly one hundred records. Rejected: a **single** importable Update Set file is mandated.
- **Roll back by reverting individual update records** rather than deleting the scope. Rejected as unreliable for a first install, where the scope and its tables did not previously exist and there is no prior version of each record to revert to.
- **No rollback at all**, leaving a failed install in place for manual triage. Rejected: it strands a half-committed scope on the instance and leaves the next deployment attempt to collide with it.
- **Take a backup before deleting.** This is the alternative a reviewer will reach for first, and it is not available: **no snapshot or restore facility exists for a personal developer instance operator.** That absence is precisely what makes the operation irreversible rather than merely destructive.
- **Read a row of each entity table for the seven table gates, as AAP section 0.11.2 words them, rather than each table's definition record.** Not available against a correctly built application, and this is the one gate-form question the delivery could not settle inside the artifact. `D-310` seals all ten tables — `access` `package_private`, `read_access` false, `ws_access` false — because three native read routes recover a premium value with no element on which a field-level control could be evaluated, so a sealed table answers `HTTP 400 Invalid table` to every external caller including an instance administrator and a literal row read would fail against a correct build. The delivered form reads each table's `sys_db_object` record and asserts its three posture values (`D-311`). Because that establishes an equivalent fact by a different route rather than the route the plan names, it is **accepted explicitly and by name** in acceptance item `B4a` of [`validation-checklist.md`](../../servicenow-startup-tracker-poc/docs/validation-checklist.md) rather than argued as equivalent (`D-455`), and the residual risk is recorded in [`gaps-and-flags.md`](../../servicenow-startup-tracker-poc/docs/gaps-and-flags.md). The same substitution is what makes the rollback's own confirmation decidable: a sealed table returns a client error whether it was deleted or merely became unreadable, so an empty metadata result decides and the direct read corroborates only (`D-262`).
- **Delete the scope on the trigger condition alone**, reading `result[0].sys_id` from the scope query. Rejected: that is one unguarded array index away from deleting a scope this deployment never created, on an instance where the scope pre-existed. The five preconditions and the operator token exist because this is the one operation in the delivery with no remedy, and a precondition is worth more here than any remedy.
- **Stretch the rollback to cover an upgrade install.** Rejected: on that instance the scope's tables, flows, portal records and data belong to a previous deployment, and destroying them is not a rollback of this one. A separate, non-destructive backout path is documented for it.
- **Record the release rather than establish it.** Rejected, and it was also the delivered form: a check that reads `glide.war` and proceeds regardless asserts nothing, because a pre-floor instance passes it exactly as a current one does and the first evidence of the shortfall is a Flow Designer capability that is absent halfway through guide 02.
- **Confirm the rollback by reading an application table.** Rejected because it cannot decide the question: the read returns a client error — `HTTP 400` on the target instance, `403` or `404` elsewhere — whether the table was removed or merely became unreadable when its controls went with the scope, so it cannot distinguish the two. It is kept only as a corroborating signal, with `400` accepted alongside `403` and `404` (`D-262`), and the `sys_db_object` metadata read is what decides.
- **Wire the XML validation into the existing GitHub Actions workflow.** Rejected — see the rationale below.

### Rationale

The contrast with the legacy deployment is the sharpest evidence available, and it runs in both directions.

**The legacy pipeline had no rollback.** `.github/workflows/cd.yml:L46` deploys production with `uses: appleboy/ssh-action@master`, whose inline script runs `docker-compose pull`, `docker-compose up -d` and `docker system prune -f` at `:L53` through `:L55`. `.github/workflows/cd.yml:L63` then lists `Implement rollback mechanism in case of deployment failure` among the workflow's own unfinished tasks. The automated path had nothing to fall back to.

**The legacy shell script did have a rollback, and it was reversible — because a database dump existed.** `scripts/deploy_production.sh:L129-L145` defines `rollback()`, which brings the containers down, resolves `LATEST_BACKUP=$(ls -td $BACKUP_DIR/backup_* | head -1)` at `:L137`, and restores with `cp -R $LATEST_BACKUP/* $DEPLOY_DIR/` at `:L139`. That restore is underwritten by a real dump taken earlier in the same script: `:L62` runs `docker exec boston_startup_tracker_db pg_dump -U postgres boston_startup_tracker > $BACKUP_PATH/database_backup.sql`.

**This is the fact a reviewer must not let be softened into "rollback is risky".** The legacy rollback restored data because a `pg_dump` existed. Scope deletion has no dump, no snapshot and no restore path of any kind. That is the entire reason it is the one genuinely irreversible operation in this delivery, and it is why the trigger conditions are enumerated as exactly two rather than left to judgement.

Two further legacy constructs are the antecedents of the target procedure. `scripts/deploy_production.sh:L4-L5` sets `set -e` and `trap 'echo "Error occurred. Exiting."; exit 1' ERR`, which is the abort-on-error posture the failure matrix formalises. `scripts/deploy_production.sh:L104-L127` defines `post_deploy_checks()`: a running-container count at `:L109`, a health probe `curl -f http://localhost:8000/health-check` at `:L115`, and a critical-test subset at `:L121`. Those three checks are the antecedent of the eleven required post-commit gates, which are their machine-checkable equivalent against a platform that has no containers to count.

**Why the validation is not wired into CI.** `.github/workflows/ci.yml:L24` runs `pip install -r requirements.txt` against a `requirements.txt` that does not exist anywhere in the repository, and `:L36-L37` runs `cd src/frontend` then `npm ci` against a directory that contains no `package.json`. A validation step added to that workflow would never reach execution, and its presence would create the false impression of an enforced gate. The validator is therefore invoked directly, as a documented pre-delivery step whose exit code blocks the deployment, and no CI or CD workflow file was modified.

**Why preview duration is a named risk rather than a footnote.** Practitioner guidance keeps an update set under roughly one hundred records and treats five hundred to a thousand as an absolute ceiling. The delivered set carries **313** `sys_update_xml` records across about 1.35 MB — inside the hard ceiling, comfortably above the comfort guideline. The runbook states the consequence plainly: the preview is the longest step in the sequence and should be expected to approach the 600-second timeout. Slowness there is not failure, and the correct behaviour is to poll to the timeout before declaring one.

The full procedure, every request shape, both poll intervals, all three timeouts, the eleven required gates, the five further checks beside them in two classes, all four acceptance-required and none rolling back — the non-rollback `GATE-COL-01` and the three `GATE-SEC` security checks — the five rollback preconditions, both rollback branches and the complete failure matrix are in [`deployment-runbook.md`](../../servicenow-startup-tracker-poc/docs/deployment-runbook.md) and [`validation-gates.md`](../../servicenow-startup-tracker-poc/docs/validation-gates.md).

### Risk level

**High**, on two independent grounds.

The rollback **destroys the application and every row of data in it with no restore path**, and its blast radius extends beyond the Update Set to every artifact built by hand inside the scope afterwards — flows, portal and theme records, widgets and ATF suites all live in the same scope. The five preconditions narrow the exposure rather than removing it: they make the operation **refusable**, so an unclean or ambiguous instance stops with a partially installed application and a referral rather than a deletion, but on a genuinely clean install a single failing required gate still discards the work of five manual build guides, and that is by design.

Separately, **a preview that runs past 600 seconds aborts a deployment that would otherwise have succeeded.** The risk here is not the timeout itself but the reaction to it: an operator who treats a slow preview as a failure and reaches for the rollback would destroy a scope over a latency problem.

## 3. Credential handling for outbound ingestion — risk High — reviewer persona API/Integration

### Decision

**What was implemented.** All outbound authentication resolves through two named Connection & Credential Aliases, referenced **by name** from the Flow Designer REST steps of the two ingestion flows:

| Alias | Authentication model | Holds |
| --- | --- | --- |
| `x_bst_startuptrk.crunchbase_api` | Basic Auth record used as an **encrypted store** | The Crunchbase API key in the password field. The provider does **not** accept HTTP Basic in any form, so the flow reads the key through the alias at run time and sends it as an **`X-cb-user-key` request header** — the wire contract at `D-229` |
| `x_bst_startuptrk.linkedin_oauth` | OAuth2 | Client identifier, client secret and refresh token. Every call additionally carries two mandatory headers, `X-Restli-Protocol-Version` and a `LinkedIn-Version` value held as the code constant `AppProperties.LINKEDIN_API_VERSION`, `202606`, per `D-266` which amends `D-236` |

**Zero credential material appears in the Update Set XML, in any flow input, or in any script step.** The aliases are built on the instance and are not shipped. The manual guide works in two record classes: it **builds the four definition records — two aliases and two connections, none of which can hold a secret — and confirms rather than creates the credential secrets**, so the credential values remain the provisioning owner's to supply. On the unprovisioned path it may build a credential **record** with every secret-bearing field empty, and it never builds LinkedIn's OAuth provider, profile or token records at all; guide 01's per-provider matrix is the authority. No step of the delivery ever writes, prints, echoes or logs a credential value — where a request or a log row must name one, it names the environment variable.

**On readiness, this entry asserts nothing.** The requirements state that live credentials are already provisioned, and that statement is an **input to the design** rather than an observation of any instance. Whether either alias currently holds credential material is a property of an instance at a moment in time, and restating it here is how a package comes to contradict itself. The single factual statement is guide 01's [`## Credential posture`](../../servicenow-startup-tracker-poc/docs/manual-build/01-connection-credential-aliases.md#credential-posture), which separates the **build** gate from the **fallback-validation** gate from the **live-validation** gate; only the third is affected by an unprovisioned alias. A reviewer should read that section rather than infer readiness from anything below.

The two API endpoints travel separately as ordinary non-secret configuration: `x_bst_startuptrk.crunchbase.base_url`, shipped value `https://api.crunchbase.com/api/v4`, and `x_bst_startuptrk.linkedin.base_url`, shipped value `https://api.linkedin.com/rest`, both read through the `AppProperties` Script Include. Neither is the value the retired legacy module pinned — `https://api.crunchbase.com/v3.1` and `https://api.linkedin.com/v2` are **stale and unreachable**, and the correction of both the code default **and** the shipped property record value is `D-229`. None of the **eleven** scoped properties holds an API key, client identifier, client secret, refresh token or password, and the one non-secret value that would have been a twelfth — the LinkedIn API version — is a code constant instead (`D-266`). The delivery ships **no** retention or minimisation property of any kind: `AppProperties` exposes accessors for those eleven and for nothing else.

LinkedIn moves from a static bearer token to **OAuth 2.0**. This is an authentication-model **upgrade**, not a port: the legacy module had no token endpoint, no refresh token and no expiry handling at all.

A deployment-time branch exists for an instance lacking the entitlement for the Flow Designer REST step: a scoped script step resolves the connection and its credential at run time **by alias name** and issues the call through the scoped outbound REST message API. That path is still alias-by-name, still spoke-free, and still inlines no secret.

**What alternatives existed.**

- **Carry the keys forward as system properties.** Rejected: a property is readable by anything that can read properties, and hard-coding a secret anywhere in the deliverable is forbidden outright.
- **Install an IntegrationHub spoke per source.** Forbidden by the requirements, and unnecessary in any case — a generic REST step bound to a credential alias is not a spoke, which is what makes the primary path both compliant and simple.
- **Keep LinkedIn on a static bearer token because it is simpler.** Rejected: there is no refresh path, so the token expires into a silent ingestion outage, and it would still have to live somewhere.
- **Pass credentials as flow inputs.** Explicitly forbidden, and it would place secret values in the flow definition and its execution history.
- **Commit the aliases inside the Update Set** so the deployment is self-contained. Rejected: an alias committed with credential material would put secrets in the delivered file, which is the one outcome the whole design exists to prevent.

### Rationale

The anti-pattern being eliminated is concrete, citable and worse than it first appears.

`src/data_collection/api_integrators/crunchbase_integrator.py:L11` declares the module-level constant `API_KEY: str = "your_crunchbase_api_key_here"`, and it is passed as a **query parameter** at three separate call sites — `:L22`, `:L41` and `:L60` — each reading `requests.get(endpoint, params={"user_key": API_KEY})`. A key in a query string is not merely hard-coded: it travels in the request URL, which means it lands in intermediary and server access logs, in browser and proxy history, and in any error report that quotes the failing URL. Moving it into a credential alias removes it from the URL as well as from the source.

`src/data_collection/api_integrators/linkedin_integrator.py:L12` repeats the pattern with `API_KEY: str = "your_linkedin_api_key_here"`, sent as a **static** bearer header at three call sites — `:L23`, `:L42` and `:L61` — each reading `requests.get(endpoint, headers={"Authorization": f"Bearer {API_KEY}"})`. Searching the module for a token endpoint, a refresh token or any expiry handling returns nothing. That absence is the precise antecedent of the OAuth 2.0 upgrade: the legacy design had no mechanism by which a credential could ever be rotated without editing source.

`.env.example:L26-L29` shows the same material in plain environment form: the header `# External API Keys` followed by `CRUNCHBASE_API_KEY`, `LINKEDIN_API_KEY` and `GITHUB_API_KEY`. The legacy modules pinned their endpoints at `crunchbase_integrator.py:L10` and `linkedin_integrator.py:L11`; **neither value was carried forward**, because both are stale and unreachable. What the delivery ships is the corrected provider root for each — `https://api.crunchbase.com/api/v4` and `https://api.linkedin.com/rest`, per `D-229` — in the two non-secret properties named above. The legacy citation stands only as the construct being replaced: the endpoint is configuration, the key is not, and the delivery separates them.

The governing platform convention is that **a credential alias resolves a connection and its credential at run time without exposing the secret to the caller**, and that the binding between a flow and an alias is **by name**. The consequence a reviewer must act on is that a name mismatch **fails at run time, not at build time**: the flow saves cleanly, the deployment reports success, and the failure surfaces only when the scheduled flow first attempts a call. This is why **resolving each alias to exactly one record** before either flow is saved is a requirement rather than a courtesy — why the resolution asserts singularity and fails closed rather than taking the first match, at `D-230` — and why the match is made on the alias record's **`sys_alias.id`** column against the dotted value the flows reference, not on its human label, at `D-390`.

Two things a reviewer should not conflate. Resolving the **API ID** to exactly one alias record — a query on `sys_alias.id` — is the build gate and is available in any credential posture. A **green authenticated probe against the provider** is the live-validation gate, and it is provider-correct rather than generic: the platform's own connection test composes neither the `X-cb-user-key` header nor LinkedIn's two versioning headers, so it can report green on a chain that no provider would accept and red on one that works. It is retained as a diagnostic and is not a completion criterion.

The property inventory, the statement that no property holds a secret, and the identification of the two aliases as the only home for credential material are in [`api-reference.md`](../../servicenow-startup-tracker-poc/docs/api-reference.md); the alias build procedure is [`manual-build/01-connection-credential-aliases.md`](../../servicenow-startup-tracker-poc/docs/manual-build/01-connection-credential-aliases.md).

### Risk level

**High.** A leaked third-party key is an immediate compromise of an external account, outside this instance's control and outside its audit trail — it cannot be contained by fixing the application. And because alias binding fails at run time rather than at build time, a name mismatch can sit undetected through a deployment that reported success in every gate, surfacing hours later as an ingestion outage whose cause is not where the operator will look first.

### Reviewer persona

**API/Integration.** Check each of the following.

1. **Scan the delivered Update Set XML and every document in the package for credential material, value-aware.** The test is a credential-shaped **name** bound to a long opaque **value** — a match on `api_key`, `apikey`, `client_secret`, `refresh_token`, `access_token`, `user_key`, `password`, `secret` or `bearer` followed by an assignment (`:`, `=`, `=>` or the word *is*) and then **16 or more** characters drawn from `A-Za-z0-9._~+/=-`. Anything matching that shape is a finding until explained. This is pre-delivery gate **G-5**, and the delivery ships the scan as an executable check rather than as prose.

   **Do not run this as a zero-hit count of the words or the placeholder strings.** Two reasons, and the first is that this very document would fail it: the words above and the legacy placeholders `your_crunchbase_api_key_here`, `your_linkedin_api_key_here`, `your_crunchbase_api_key` and `your_linkedin_api_key` are **quoted here, in this instruction**, so a reviewer counting raw occurrences would fail the delivery on the text telling them to check. The second reason matters more: a word count also **passes** a real secret whose variable happens not to be on the list. A value-shaped test has neither property. The decision to replace the earlier zero-hit instruction is `D-250`.

## 4. The data-integrity cluster — join-table authority, cascade rules and the stored portfolio count — risk Medium — reviewer persona Data/SME

### Decision

Three related choices, each of which a competent engineer could reasonably have made differently, and each of which the requirements left open.

**4a. `x_bst_startuptrk_m2m_round_investor` is authoritative for participation, and the List column is a one-way projection of it.** The join table holds one row per funding-round-to-participating-investor link, and it is **the only table written when participation changes**. A unique composite index on `(funding_round, investor)` is declared in the Update Set, so the same investor cannot be linked to the same round twice by any write path, and the programmatic writer is idempotent.

Three surfaces read it. The funding-round form surfaces it as a **related list**, which is the editable participant surface. The REST layer assembles `participating_investors` as a **JSON array** from the join table directly, one batched query per page rather than one per round. And `x_bst_startuptrk_fundinground.participating_investors` exists as a `glide_list` column that is **calculated, virtual and read-only** — a **one-way derivation** whose dictionary entry carries `virtual` true and a calculation that calls `InvestorPortfolioService.participantList()`, so the value is computed from the join table on every read. Nothing is stored, so there is no refresh, no second write target and nothing that can drift; a write arriving through the Table API, the native form or an import transform cannot persist at all. **Nothing writes both.** The derivation is bounded and the bound is enforced: at 33 characters per member the declared length of 4000 renders 121 investors, and a round linking more is reported at warn severity with the value cut at a whole identifier; a value that exceeds the declared length even so is reported at error severity and rendered empty rather than part way through an identifier, because a truncated identifier list is indistinguishable from a complete one when read. Either way the join table remains the complete record.

`lead_investor` remains a first-class reference column on the funding round, which is how the lead-versus-participating distinction is carried at all.

**4b. Cascade delete on every mandatory child reference, and on both join-table parents.** Nine reference columns exist across the ten tables. The five mandatory `startup` references on Founder, Executive, Funding round, Job posting and News article cascade, as do both mandatory join-table references. The two **non-mandatory** references deliberately do **not** cascade: `x_bst_startuptrk_fundinground.lead_investor`, so deleting an investor leaves a round that named it as lead standing rather than destroying funding history; and `x_bst_startuptrk_rate_limit_counter.caller`, whose closed windows are removed by a scheduled pruning job instead. A cascade delete fires the portfolio business rules, so the derived count stays correct through a cascade.

**4c. `portfolio_count` is a stored integer maintained by business rules.** It is the count of **distinct** startups over the **union** of two traversal paths: funding rounds whose `lead_investor` is the investor, and funding rounds reached through the join table. The lead path is a grouped read over the funding rounds keyed by startup; the participation path resolves the investor's link rows to startups in batches of at most 200 round identifiers, so no query is handed an unbounded list. **The two result sets are keyed into one set before the size is taken**, which is what makes a company reached by both paths count once. The column is `read_only`, and the REST investor create and update operations separate the fields they accept from the fields they return, so a request body naming `portfolio_count` is ignored rather than applied.

Two business rules maintain it, both delegating to one service so the derivation exists in exactly one place, and each recalculating only the investors its trigger affects. The funding-round rule fires after insert, update and delete: on an update it recalculates **both** the previous and the new `lead_investor` and handles a change to the round's `startup`; on a delete it recalculates the deleted round's lead investor and every investor linked to it through the join table. The join-table rule fires after insert, update and delete: it recalculates the row's investor and, on an update, the previous row's investor, and it refreshes the projection on **both** the current and the previous funding round. A recalculate-all method reads the graph in two passes and then writes only investors whose stored value differs, so a recalculation over an already-correct table performs zero writes and returns the number it did write.

**What alternatives existed.**

- For 4a: **a list-reference column alone**, storing delimited identifiers on the funding round and creating no table at all. Rejected because the requirements name the physical join table explicitly. And **implementing both as independent records of participation** — the obvious reading, and the one that fails: two writable representations of the same fact drift apart. The delivered design keeps both mechanisms the requirements name while making one of them strictly derived and read-only, which is what removes the dual write rather than merely documenting it.
- For 4b: **clearing the reference** instead of cascading, or **blocking the delete** outright. Either is a defensible engineering choice, which is exactly why this needs an entry. Clearing was rejected because a mandatory reference cannot legally be left empty, and orphaned funding rounds would corrupt the portfolio-count derivation by counting rounds belonging to deleted startups. Blocking was rejected as making routine data correction impossible. Cascading on the non-mandatory references was also rejected, in the other direction: it would have let deleting one investor destroy funding history.
- For 4c: **a dictionary-level calculated value**, evaluated on read. Rejected: it re-runs a two-table traversal on every read and can be neither queried nor sorted efficiently. **Recomputing every investor on any change.** Rejected as quadratic in the data volume. **Counting without unioning first.** Rejected because it double-counts, which is the specific error the reviewer check below is designed to catch.

### Rationale

Every part of this cluster is new semantics rather than a port, and the legacy schema is the evidence.

`src/backend/models/funding_round.py:L6-L9` defines the legacy association table `funding_round_investors` with **exactly two foreign-key columns**, `funding_round_id` and `investor_id`, **and nothing else** — no lead flag, no role column, no ordering. `:L23` declares a single undifferentiated `investors` relationship, and `:L40` serialises it as a **flat list of names**, `result['investor_names'] = [investor.name for investor in self.investors]`. A consumer of the legacy API could not tell a lead investor from a participant, because the schema did not record the difference. The lead-versus-participating distinction is therefore introduced by this delivery, which is why it needed a decision at all.

`src/backend/models/investor.py:L9-L12` declares the entire legacy Investor model: `id`, `name`, `type` and `website`. There is **no `portfolio_count`, no `aum_usd` and no `focus_areas`** anywhere in it. The derivation has no legacy precedent of any kind, so every element of its semantics — which paths count, whether they union, whether the value is stored or computed, and when it is refreshed — is a fresh decision rather than a transcription.

`src/backend/models/startup.py:L24-L28` declares exactly the five child relationships `founders`, `executives`, `funding_rounds`, `job_postings` and `news_articles`. A search across every model file for `cascade` or `delete-orphan` returns **nothing**: the legacy schema left orphan behaviour entirely undefined. The requirements are equally silent on it. A cascade decision was therefore unavoidable rather than optional — the only way to avoid making it would have been to ship a schema in which deleting a startup produces rows whose mandatory reference points at nothing.

The delivered model, its nine reference columns with their individual cascade settings, the calculated projection with its declaration and its bound, and the two-path derivation with its batching are specified field by field in [`data-model.md`](../../servicenow-startup-tracker-poc/docs/data-model.md).

### Risk level

**Medium**, and the placement is deliberate in both directions.

It sits **below** the three High entries because the failure modes are data-correctness problems, not exposures: a wrong count misinforms, an orphaned row confuses, and both are repairable by re-running a recalculation. No credential leaks and no entitlement boundary moves.

It is **not Low** for two reasons. First, a stored aggregate **drifts silently** if data arrives through a path that skips business rules — an import transform with rule execution disabled is the realistic case, and nothing about the resulting wrong number looks wrong. Second, the union-before-count rule is easy to implement in a way that double-counts an investor's company when that investor both led one round and participated in another round of the same company; the delivered implementation keys both result sets into one set before taking the size, and a reviewer should verify that behaviour rather than assume it.

### Reviewer persona

**Data/SME.** Check each of the following.

1. **Run the same ingestion batch twice and count.** Seed a batch containing at least one of each of the six record types, run the orchestrator, record the row count of each of the six tables, then run the **identical** batch again and record the counts a second time. **Every count must be unchanged.** A count that doubled is the defect this subsection exists to prevent, and it is invisible to any test that runs the batch once. Confirm on the second pass that the outcome reports the rows as duplicates or updates rather than as fresh insertions. Confirm too that the natural identity keys are a **judgement about identity** — two genuinely distinct rounds of the same type on the same date for one startup collapse into one — and that the consequence is acceptable for the data in hand; the keys are listed at `D-238`.
2. **Verify the match is tolerant and then confirmed, in both directions.** Seed a stored row with leading and trailing whitespace and mixed case, then ingest the same record with different whitespace and different case: it must **update** the stored row, not insert a second. Then ingest a record whose name is a **prefix** of a stored name: it must **not** match. Both behaviours are required — a matcher that satisfies only the first is over-eager and one that satisfies only the second is the exact-equality prefilter this replaced.
3. **Verify a child resolves its parent by the whole composite key.** Create two startups with the **same name** in different headquarters locations. Ingest a founder naming one of them by name **and** headquarters and confirm it attaches to the right parent. Then ingest a child that supplies the name only, and confirm it is **refused with a stated reason** rather than attached to whichever parent the query returned first.
4. **Verify an unreconciled round is not reported as processed.** Cause one participant link of a funding round to fail, and confirm the round's own `import_state` is set to `error` and the run summary counts it in **`skipped`** — not in `processed`, and not in `rejected`. There is **no `partial` counter** on any delivered surface: the `run_summary` event publishes exactly nine members — `provenance`, `source_system`, `processed`, `rejected`, `skipped`, `duplicates`, `unmatched`, `rule3_deviations` and `events_dropped` — and the object `writeRunSummary()` returns carries eleven, `{ run, processed, rejected, skipped, duplicates, unmatched, rule3_deviations, source_system, provenance, events_dropped, logged }`, where `logged` reports only whether that event was rendered. Any member beyond those is a defect. Because `skipped` also carries per-record application errors, confirm the run's **events** name which cause applied; the decision is `D-412`.
5. **Verify the distinct union directly with the double-count case.** Create an investor that **leads** one round of company A and **participates**, through the join table, in a second round of the **same** company A. Confirm `portfolio_count` reads **1**, not 2. This single test is the highest-value check in this entry.
6. **Verify each traversal path independently**: an investor reachable only as a lead, and an investor reachable only through the join table. Both must count.
7. **Verify the update triggers.** Change a round's `lead_investor` and confirm **both** the previous and the new investor are recalculated. Change a round's `startup` and confirm the count follows. Re-point an existing join row and confirm both the previous and the new investor are recalculated **and** that reading `participating_investors` on both the previous and the new funding round returns each round's join set — there is no refresh to wait for, because the column is calculated on read.

9. **Verify the deliberate non-cascades.** Delete an investor that is named as `lead_investor` on a round and confirm the **round survives** with its reference as it stands — this is intended behaviour, not a dangling-reference defect. Confirm rate-limit counter rows are removed by the pruning job and not by a `sys_user` deletion.
10. **Verify the one-way derivation rather than assuming it.** Confirm `participating_investors` carries `read_only` true **and `virtual` true with a calculation that calls `InvestorPortfolioService.participantList()`**; confirm that method writes nothing, so **no** code path writes the column and a write to it cannot persist; confirm the REST array is assembled from the **join table** and not from the column; and confirm the form's related list reads and writes the **join table**. **Do not raise the existence of the List column as a defect** — it is present by design as a derived projection, and the requirement it satisfies is the List type the specification declares. The defect to look for is the opposite: any second writer to that column, or any consumer that reads the column where it should read the join table.
11. **Verify the projection's overflow behaviour** by linking more investors to one round than the declared length can hold. The projection must be **emptied and the overflow logged**, never truncated to a partial list, and the REST array and the count must both remain correct because neither depends on the projection.
12. **Verify the composite uniqueness constraint** by attempting to link the same investor to the same round twice through each available write path, including the programmatic one.

16. **Verify drift control after a bulk load.** Confirm business rules ran during the staging CSV load, confirm the recalculate-all method was invoked from a background script afterwards, and then compare the stored counts against a freshly recomputed set. A recalculation over a correct table should report zero investors written; a non-zero figure is the drift signal.
17. **Verify the projection write is checked rather than assumed.** Make one investor's projection unwritable and confirm the recalculation **reports** a stale projection at error severity and completes the rest of the batch — neither aborting the batch nor reporting success. An unchecked write is how a derived column diverges from its source with no signal at all; the decision is `D-273`.
18. **Verify identity matching does not depend on the database collation.** Confirm the de-duplication query narrows with a two-way prefix and that the comparison which actually decides runs in script. A match that relies on the instance database comparing case-insensitively will deduplicate on one instance and duplicate on another, from the same payload — and the stored normalised key that would be the cleanest fix is unavailable, because the field list is binding and complete. The decision is `D-272`.

19. **Verify de-duplication converges on the rendered name, and that the invariant is the one you expect.** Stage five spellings of one company that all *render* `Widget Works` — the plain name, a lower-case one, one padded with spaces, one carrying a leading `U+FEFF`, one carrying a trailing `U+202E` — and two that render `WidgetWorks`, differing from each other only by a `U+200B` against a `U+00AD`. All seven share one headquarters location. The correct outcome is **two** accepted rows, one per distinct rendered name, and **no** accepted `name` carrying any member of the zero-width and directional formatting class. Two things would each be a defect: three or more rows, which means a stored value still carries a character that paints nothing and two rows a reader cannot tell apart now exist; and **one** row, which means a space was substituted for the invisible character, and the same substitution would merge two genuinely distinct company names. Then confirm the same seven spellings written through `POST /startups` and typed into the platform form view produce the identical two stored values, because all three paths must read their text through one definition.

Confirm `errors` is a **subset** of `skipped` and never added to it, and confirm the run's unhealthy reason reads `write_failures` when a row failed to write rather than the ambiguous `operational_skips`. Per `D-529`.

## 5. Interface deviations from the legacy surface — risk Medium — reviewer persona UX

### Decision

**What was implemented.** A Service Portal experience — one portal on the url suffix `bst`, one theme, five pages `bst_home`, `bst_company`, `bst_investor`, `bst_dashboard` and `bst_account`, and eight widgets — carrying three deliberate deviations from the legacy React surface.

**5a. The company profile is cut from six tabs to five.** The delivered tab strip is exactly **Overview, Funding, People, Jobs, News**, in that order and with those labels. Three things changed at once, and all three must be stated: "Similar Companies" is **dropped outright**; "Team" is **re-specified as "People"** and now carries founders **and** executives together in one pane; and the **order changed**, so Funding moves from third position to second and People sits third.

**5b. Routing is query-parameter based.** Pages are addressed as `/bst?id=<page>`, and a record-scoped page adds `&sys_id=<record>`. `/bst` with no `id` resolves to the home page. Inside a widget template links are written relatively as `?id=…`, so the portal suffix is never hard-coded into a widget.

**5c. 1024 pixels is the declared supported viewport floor.** Only medium and large Bootstrap column classes are authored. No extra-small or small refinement exists: no `col-xs-*`, no `col-sm-*`, no `hidden-xs`, no `visible-sm-*`, and no media query keyed to the extra-small or small breakpoint. A viewport narrower than 1024 pixels is out of scope and is not a defect.

Two supporting points belong to this entry because they are what a UX reviewer will look for. **The premium treatment has exactly two forms, one for each granularity, and both are present together on a surface that has a denied field.** At **field** granularity the denied position carries a `<span class="label label-info">Premium</span>` — never a blank, an empty cell, a zero or a dash, and never `.label-default`, which this portal reserves for categories. **Once per surface**, at its end, the reusable `bst-premium-upsell` widget renders one `.alert.alert-info` with one `.btn.btn-primary`; it has three hosts, the company profile, the investor profile and the account summary, and is placed on no page of its own. And the portal's sole icon source is the **platform glyph font**: never Lucide, which is confined by rule to the executive deck. The instruction runs both ways.

**What alternatives existed.**

- For 5a: **keep six tabs**, leaving "Similar Companies" empty or populating it from a heuristic such as shared industry. Rejected — an empty tab advertises missing functionality, and a heuristic would present invented data as fact. **Keep the label "Team"** rather than renaming. Rejected: the five tab names are specified, and the pane's contents changed anyway, since it now carries executives as well as founders. **Keep the legacy tab order.** Rejected: the specified order is part of the specified tab list.
- For 5b: **implement URL rewriting** to preserve path-style routes such as `/company/<id>`. Rejected as disproportionate — five routes are mandated, their URL syntax is not, and a rewriting layer would add a failure mode to every deep link in exchange for cosmetic parity with an application that never ran.
- For 5c: **author extra-small and small breakpoints anyway.** Rejected: viewports below 1024 pixels are explicitly out of scope, and as the rationale shows there was no responsive behaviour to preserve.
- On the upsell: **hide gated fields silently.** Rejected — a blank cell is indistinguishable from a genuinely empty column, so silent hiding conceals the entitlement boundary from the very user it applies to and makes the product look broken rather than tiered.

### Rationale

**The dropped tab was forced, not chosen.** `src/frontend/components/CompanyProfile/CompanyProfile.tsx:L86-L91` renders six tabs in the order Overview, Team, Funding, Jobs, News, Similar Companies. `:L112` binds the sixth to `companyProfile?.similarCompanies` — a field with **no counterpart anywhere in the binding schema**, which declares no competitor or similarity column on any of the seven entity tables. There is no data to render. That absence *is* the rationale; keeping the tab would have required either an empty pane or invented data.

**The routing change replaces routes that were never served.** `src/frontend/App.tsx:L29-L37` declares five path-style routes with `:id` parameters — `/`, `/search`, `/company/:id`, `/investor/:id` and `/user/:id` — which is the antecedent of the five target pages and of the query-parameter form that replaces them. The platform convention is decisive here: Service Portal addresses pages by query parameter, so the path form is not reproducible without URL rewriting. Worth noting alongside it, `src/frontend/App.tsx:L12` imports `./styles/theme`, a module that was never authored — the styles directory contains only `global.css` — so the legacy application could not have rendered any of those five routes in the first place.

**The 1024-pixel floor discards nothing.** `src/frontend/styles/global.css` is the repository's entire design-token and responsive surface: 41 lines, of which a search for `media` returns **not one match**. There was no responsive behaviour at any breakpoint, so declaring a floor removes no existing capability and closes no previously supported viewport. The same file hard-codes `background-color: #f5f5f5` at `:L8`, `color: #1976d2` at `:L14` and `max-width: 1200px` at `:L24`, which is why the target declares design tokens in the theme record instead of literals in widget CSS — and why the Material-UI component vocabulary has no carry-over at all, the platform design system being Bootstrap 3.3.6 with AngularJS.

The portal build, the fixed tab list, the routing table with its fifteen navigation hops, the floor's exact mechanics, the upsell substitution rules and the iconography constraint are specified in [`manual-build/04-service-portal-pages-and-widgets.md`](../../servicenow-startup-tracker-poc/docs/manual-build/04-service-portal-pages-and-widgets.md).

### Risk level

**Medium.** These deviations are visible to every user and to any stakeholder comparing the result against the legacy screens, so they carry real expectation-management risk and should not be discovered at a demonstration. The upsell treatment additionally sits directly on the entitlement boundary: if it renders where it should not, or fails to render where it should, a user's understanding of what they are entitled to is wrong.

They are nonetheless **reversible and non-destructive**, which keeps them below the three High entries. A tab can be added, a route rewritten, a breakpoint authored, a label changed. Nothing is lost that cannot be restored, and no data or credential is at stake.

## Rule 3 call-out coverage

The **Critical Decision Review Document** rule requires three categories to be called out explicitly. All three are discharged below, so a reviewer does not have to infer the coverage.

### Irreversible operations — entry 2

**Branch A of the entry 2 rollback — scope deletion — is the one genuinely irreversible operation in this delivery, and it is the only one.** Deleting the `x_bst_startuptrk` scope record cascades its ten tables, all data in them, its three roles and every artifact built inside it. It is reachable only where pre-flight 2 recorded `START_STATE=clean`, which bounds it to destroying what the same run created; the `existing` starting state routes to the non-destructive back-out of Branch B instead. No snapshot, dump or restore facility is available to a personal developer instance operator, which is exactly what distinguishes it from the legacy rollback it replaces — that one restored data because a `pg_dump` existed at `scripts/deploy_production.sh:L62`.

The claim is bounded deliberately, because an unbounded warning is ignored. Everything else in this delivery is recoverable:

- **Nothing is deleted from the repository.** The entire legacy tree is retained read-only, and the repository `README.md` is the only legacy file this delivery modifies at all.
- **The Update Set import is preview-then-commit.** A problem found at preview costs nothing: the set has not been applied, and the remedy is to fix the source and re-import. Every failure condition before the commit resolves without touching the scope.
- **The pre-delivery gates run against files, not against the instance.** A file that fails validation has never reached the instance, so a failure there has no blast radius at all.
- **Neither of the two non-gate check classes rolls back, but only one of them blocks acceptance.** `GATE-COL-01` is **acceptance-required and non-rollback**: a failure leaves the installation in place and blocks acceptance until the Update Set is corrected and re-imported, because criterion 1's 53-column requirement depends on it. `GATE-SEC-01` through `GATE-SEC-04` are **non-normative**: they are recorded and investigated and block nothing. Each of the five has its own non-destructive remedy. `GATE-SEC-04` is the one check in the set that is not an HTTP request — it is a background script run inside the scope, and it exists because sealing the ten tables closed every external read route, so the one remaining ACL-respecting path is worth exercising after the commit (`D-310`, `D-311`). The instance's XML parser configuration is **not** among these checks: it is the platform owner's and is asserted as a prerequisite before the import rather than gated after the commit (`D-256`). The classes are recorded at `D-108`. **No gate in this delivery reads or writes anything outside the `x_bst_startuptrk` scope**, so no gate failure is remediable by an instance-wide configuration change and none is exempted from the acceptance set on that ground.
- **A rollback against a pre-existing installation is not authorised at all.** Where the scope existed before the run, the remedy is the non-destructive back-out of Branch B, so the irreversible operation is unreachable in precisely the situation where it would be unrecoverable.
- **The deletion is refusable, and refusing is the designed outcome on an unclean instance.** Five preconditions stand between the trigger condition and the `DELETE`, and an `upgrade install` gets a non-destructive backout path instead. A partially installed application on an instance whose scope pre-existed is recoverable; a deletion that removed someone else's scope is not.
- **A parser-property shortfall does not roll back.** It is instance configuration this Update Set does not own, so it is asserted as a prerequisite before the import rather than as a gate after the commit, and its remedy is to set the property and re-run the assertion (`D-256`).

### Authorization decisions — entry 1, with entry 3 adjacent

**Entry 1 is the authorization decision**: moving the entitlement boundary out of application code and into 49 platform access controls, with seven field-level read ACLs as the premium gate and denied keys omitted rather than nulled. Its most consequential property is that both of its failure modes are silent and that the administrator override makes a careless verification produce documented false confidence.

**Three further authorization decisions sit inside entry 1's reviewer checks rather than in entries of their own**, and the decision log flags all four alongside entry 1's own.

The first is the disposable, web-service-access-only identity the REST test suite mints and destroys inside its own transaction, at `D-246`. It is an authorization decision because it settles what a test identity may do — non-interactive access only, no elevated role, and no persistence beyond the test — and because the alternative delivered originally was a persistent credential created outside the application scope. Note precisely what is **not** claimed: the identity holds a **working password while the test runs**, because that is what lets the inbound assertions authenticate, so the guarantee is that it is destroyed rather than that it is harmless. The three mechanisms that deliver that guarantee are at `D-292`, and the requirement that the password be cryptographic random material is at `D-295`.

The second is the table posture, now at `D-310`, which supersedes `D-254`: which routes reach the application's rows at all. `D-254` opened cross-scope read and the native Table API on the seven entity tables while closing both on the three supporting tables; `D-310` closes them uniformly on all ten, because a query predicate, the Aggregate API and an unsecured cross-scope read each recover a premium value with no element on which a field-level control could be evaluated. The consequence for review is that the Scripted REST API is the only route on which a field-level denial is observable at all — which is why check 7 asks for the closure of the other three to be **proved** rather than assumed.

The third is at `D-267`: the aggregate that produces `total_count` is authorized by a role test rather than by a probe read, so a caller holding none of the three scoped roles is answered `403` rather than a number. What that gate protects is the **size** of a set rather than any field value, and it is equivalent to a per-row check only while record-level visibility stays identical across the three roles — which is recorded as an invariant, not a coincidence.

All three are reviewed as part of entry 1 rather than separately because the same reviewer, checking the same override trap, is the person who should see them.

**Entry 3 is the adjacent authentication and credential decision**: how the application proves its own identity to Crunchbase and LinkedIn, and why no secret appears anywhere in the deliverable. The two are separate concerns and are reviewed by different people — entry 1 governs what a caller may read from this application, entry 3 governs what this application may read from elsewhere — but a reviewer of either should be aware of the other, because a bypass in one makes the other's controls moot.

### Assumptions that resolved an ambiguity in the request

Four requirements were internally ambiguous. Each was resolved by an explicit assumption rather than by silent choice, and each is stated here with what would change if the assumption is wrong. The fourth was identified during remediation, and it differs from the first three in kind: it is not an under-specification but a **collision** between two statements of the same authority.

**Ambiguity 1 — `institutional_funding_last_5yrs` appears in two mutually awkward lists.** It is named both among the fields relevant to the startup inclusion criteria and among the seven premium-gated fields.

*Assumption.* The operative inclusion rule names only two conditions: `active` = true, **and** `headquarters_location` containing "Boston" or "Cambridge, MA" as a case-insensitive substring. The filter therefore tests **exactly those two columns**, and `institutional_funding_last_5yrs` remains a premium-gated **display** attribute that takes no part in the predicate. The two location tokens are read from a system property, so they are configurable without a code change.

*Why this matters concretely.* The base `x_bst_startuptrk.user` role **cannot read** `institutional_funding_last_5yrs` — that is the point of entry 1. Had the inclusion filter depended on it, the portal search results would have been unbuildable for precisely the role that uses them most: the filter would have needed a value its caller is denied. The two requirements are only simultaneously satisfiable under this reading.

*If the assumption is wrong* — if the field was genuinely intended as a third condition — then either the field must cease to be premium-gated, or the filter must be evaluated with elevated privilege on the caller's behalf, which would be the first deliberate hole in entry 1's enforcement. Neither is a small change, which is why this is flagged rather than quietly adjusted. **Nobody should "correct" the filter to add the field without reopening entry 1.** The corresponding flag is carried in [`gaps-and-flags.md`](../../servicenow-startup-tracker-poc/docs/gaps-and-flags.md).

**Ambiguity 2 — `participating_investors` is described as a "List" field while a physical join table is named in the same clause.** These are two different platform mechanisms: a list column stores delimited identifiers inside the funding-round row and creates no table, whereas a join table is a separate physical table with its own rows.

*Assumption.* Both statements are honoured without a dual write. The **join table is authoritative** and is the only write target for participation; the **related list** on the funding-round form delivers the List user experience; the **REST array** delivers the list-valued attribute an API consumer expects; and the **List column exists as a calculated, virtual, read-only derivation** of the join table, computed on every read. Nothing writes both.

*If the assumption is wrong* — if the List column was intended as the authoritative store — the join table becomes redundant, and the calculated column has to become a stored, written one whose writer is the participation writer instead. The migration is mechanical but it inverts the direction of every write path enumerated in entry 4. See **entry 4**, and note its explicit instruction not to raise the column's existence as a defect.

**Ambiguity 3 — "exactly 7 custom tables" is stated while an eighth join table is named and a staging table is separately required.**

*Assumption.* The seven-table count governs **entity** tables. The join table, the ingestion staging table and the rate-limit counter table are **supporting artifacts**, documented separately and counted separately. Ten physical tables ship, and the success criterion is evaluated against the seven entity tables — which is why the eleven required gates contain exactly seven table gates, over those seven entity tables and no others. The four further checks reach further without changing that contract: `GATE-COL-01` counts columns across the same seven, and `GATE-SEC-01` and `GATE-SEC-02` assert the access posture across all ten.

*If the assumption is wrong* — if the count was meant to bind the physical table total — the delivery is three tables over budget, and no combination of the three can be removed without losing a stated requirement: the join table is named explicitly in the requirements, the staging table is mandated as the fallback dataset's home, and the counter table is what makes the specified rate-limit response body expressible with a computed retry value. The count would have to be renegotiated rather than met.

**Ambiguity 4 — cleaning rule 3 mandates coercing an unmatched choice value to "Other", while the field definitions that fix the choice lists declare themselves binding and complete and name no "Other" member in six of the eleven delivered entity choice lists.** The eleven divide five to six: `startup.industry`, `founder.title`, `executive.title`, `investor.focus_areas` and `jobposting.department` **do** declare `Other`; `startup.funding_stage`, `startup.employee_count_range`, `investor.type`, `fundinground.round_type`, `jobposting.remote_type` and `jobposting.seniority` do **not**. Four further choice lists exist on the supporting tables — fifteen in total across the ten tables — and none of them is reached by cleaning rule 3.

*Assumption.* Neither statement is preferred silently. Where an `Other` member exists the rule is applied exactly as written. Where it does not, the field is **left unwritten** and the event is logged with a distinct outcome and counted in a dedicated `rule3_deviations` counter separate from the general `unmatched` count and **asserted at two per source** in the flow suite (`D-403`), so the shortfall is a number an operator can read rather than a behaviour they must infer. The record itself is kept, because the rest of it is valid and mandated. Cleaning rule 3 is therefore reported as **PARTIAL** — in the traceability matrix, in the gap inventory, in the flow guides and in an ATF assertion — and not as implemented.

*Why this matters concretely.* The two available silent resolutions are both worse than the deviation. Adding an `Other` member to six binding choice lists breaches the field definitions, which are the narrower and more explicit statement and which the acceptance criteria check column by column. Rejecting the whole record — which an earlier reading of `D-022` wrongly claimed was the delivered behaviour — discards mandated data over one imprecise field, and would make an ordinary vocabulary drift at the provider look like a data outage.

*If the assumption is wrong* — if the choice lists were intended to be extensible — the fix is six new choice records and a one-line change in the mapper, and the `rule3_deviations` counter then permanently reads zero, which is exactly the signal that would confirm it. **Nobody should add an `Other` member without reopening the field-list fidelity gate**, because that gate counts columns and choices against the binding list. The corresponding flag is carried in the gap inventory.

**Decision log:** *The startup inclusion filter tests only active and headquarters_location* (`D-029`); *The join table is authoritative and the List column is a one-way projection* (`D-010` with `D-011`, the projection delivered as a calculated, virtual column per `D-434` and completed in the artifact at `D-448`); *Exactly seven entity tables, with three supporting tables counted separately* (`D-008`); *An unmatched choice value left unwritten, logged and counted* (`D-232`); *A disposable web-service-access-only test caller* (`D-246`, with `D-292` and `D-295`); *One uniform sealed posture across all ten tables* (`D-310`, superseding `D-254`); *A role test authorizing the aggregate count* (`D-267`).
